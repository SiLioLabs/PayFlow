#1 Overly broad token allowance + pay-per-use drain if daily limit not set

Severity: High — user funds at risk

Location: contract/src/lib.rs:pay_per_use, contract/src/fee.rs:transfer_pay_per_use, contract/src/spending_limit.rs, frontend/src/stellar.ts:getAllowance / buildApproveTx, components/AllowanceDisplay.tsx, components/DailyLimitCard.tsx, DailyLimitModal.tsx

Description

Subscribing approves the contract to transfer_from the user's SAC token. Recurring charge() is bounded by fixed amount/interval, but pay_per_use and pay_per_use_to pull arbitrary amounts on demand. If a user approves a large allowance (or infinite) and never calls set_daily_limit, a buggy or compromised frontend/merchant integration can repeatedly call pay_per_use until allowance is exhausted. spending_limit::enforce_limit only checks when a limit is present (Some(limit)); otherwise spending is uncapped by that control.

Impact

  • Single compromised merchant or wallet-signed promise can drain allowance without further user prompts.
  • Fees are counted toward the daily limit, but do not reduce net received — UI that only shows “merchant received” misreads budget.
  • Shared pool across pay_per_use and pay_per_use_to means “pay to custom recipient” uses the same budget — easy to miss without UX.

Reproduction (static)

1. subscribe(user, merchant, amount=5 XLM, interval, token, ...)  — approve 1_000 XLM
2. (do NOT call set_daily_limit)
3. pay_per_use(user, 100 XLM)  — succeeds, repeated until allowance gone
4. get_daily_limit(user) → None, get_daily_spent → 0, DayStart → false — no warning

Recommendation

  • Product: Proactively surface limit / spent / remaining + reset timing (day_start) in the pay-per-use flow and block the wallet prompt when amount > remaining (implemented in this PR: PayPerUseForm.tsx:remaining, DailyLimitCard.tsx progress + “resets ~24h after first spend”). Simulate before signing to catch DailyLimitExceeded (code 24).
  • Allowance hygiene: Encourage minimal allowances via AllowanceDisplay + IncreaseAllowanceModal; document “approve exactly what you need” in docs/SECURITY.md and the subscribe flow.
  • Defaults: Consider prompting for a daily limit during subscribe (or defaulting to e.g. 2× subscription amount) — currently opt-in.
  • Docs: docs/DAILY-LIMITS.md:413-420 already lists UX recommendations; enforce them in UI.

Status

Acknowledged. This PR (Issues #845 / 050) adds getDayStart + getDailyLimitStatus helpers, remaining/progress UI, and pre-wallet validation. Formal audit still required before mainnet (SECURITY.md roadmap).

#2 Single admin key with broad, pause/fee/whitelist powers

Severity: High — protocol-wide trust

Location: contract/src/admin.rs, contract/src/lib.rs:freeze_merchant / set_subscription_amount / propose_fee / pause_contract, docs/SECURITY.md:60-99 auth matrix

Description

The contract admin can freeze merchants, adjust subscription amounts/intervals, set minimum interval, propose/commit fee and grace-period changes, toggle whitelist, pause the whole contract, clear merchant revenue history, upgrade via two-step propose/commit, and batch-pause subscriptions. The auth matrix documents this correctly. Until governance is tightened, the admin key is a single point of compromise. This is by design pre-audit, but the blast radius is high: a compromised admin could pause the protocol, redirect fees, or whitelist a malicious merchant.

Impact

  • Stolen admin key → can pause charges, change fees, or upgrade the contract (upgrade authority review noted in docs/SECURITY.md:122-140).
  • Admin powers are documented as “broad and should be treated as high trust until governance is tightened” — but frontend does not surface this risk to merchants/users.

Reproduction (static)

// As admin:
propose_fee(new_collector, 500) → commit_fee()  // fee now 5%
freeze_merchant(victim, None)                     // blocks new subs
pause_contract()                                 // all charge/pay_per_use panics
// All require admin.require_auth(); verify via
//   contract/src/admin.rs:require_admin

Recommendation

  • Governance: Move admin to a multisig or timelock before mainnet; publish the audit-candidate WASM hash and freeze non-essential admin powers post-audit.
  • Two-step: Keep existing two-step flows (transfer_admin/accept_admin, propose_fee/commit_fee, propose_grace_period/commit_grace_period, propose_upgrade/commit_upgrade) and add UI confirmation (“You are performing an admin action — this is high trust”).
  • Monitoring: Index fee_proposed / fee_committed / paused events for alerts; keep ContractPauseBanner as the single source of truth (already sticky, z-index 300).
  • Docs: Tighten docs/SECURITY.md “Admin powers are broad” into a checklist with owners before mainnet.

Status

Acknowledged — documented in docs/SECURITY.md:142-148 known limitations and audit roadmap. No code change in this PR beyond surfacing the risk; governance hardening is a follow-up.

#3 Storage TTL expiry & keeper liveness (temporary + persistent)

Severity: Medium — availability & accounting

Location: contract/src/spending_limit.rs:LEDGERS_PER_DAY=17_280, contract/src/storage.rs, contract/src/lib.rs:extend_subscription_ttl / bump_instance_ttl, docs/DAILY-LIMITS.md:58-102, docs/SECURITY.md:104-122

Description

Daily-limit keys (DailyLimit, DailySpent, DayStart) live in temporary storage with TTL ≈ 17,280 ledgers (~24h). DailyLimit can expire after ~1 day of inactivity, silently removing the cap (get_daily_limit → None) while DayStart remains until its own window expires — a confusing mid-transition (docs/DAILY-LIMITS.md:199-204). Separately, subscription entries are in persistent storage but can be archived if TTL is not refreshed; users must call extend_subscription_ttl. The keeper (charge/batch_charge) is an external liveness dependency with no decentralized dispute layer.

Impact

  • User sets a cap, goes inactive for a day, limit expires — next pay_per_use is uncapped until they re-apply.
  • Spend window is ledger-count based, not wall-clock; “resets at midnight” assumptions fail. Testnet ledgers are less regular.
  • If persistent TTL is not bumped, Subscription can be archived (entryExpired / -32700) and reads fail until extend_subscription_ttl / SubscriptionRepairPanel.
  • Keeper downtime → delayed charges; no on-chain retry — users may miss grace windows.

Reproduction (static)

// From contract/src/test.rs: test_daily_limit_day_start_boundary
set_daily_limit(user, 10 XLM);
pay_per_use(user, 4 XLM);          // DayStart created, DailySpent=4
// Advance 17_281 ledgers
env.ledger().sequence_number += 17281;
pay_per_use(user, 8 XLM);          // passes — DayStart expired, spent reset to 8
get_day_start(user) → None→ fresh window

// Allowance TTL edge:
set_daily_limit(user, 5 XLM);      // TTL ~1 day from now
// wait ~1 day inactive, then pay_per_use → limit is None, uncapped

Recommendation

  • UI: Show limit / spent / remaining + “resets ~24h after first spend today” + progress bar; warn when a previously known limit becomes None (TTL expiry) and offer to re-apply (done in this PR).
  • Refresh: Auto-bump persistent TTL on lifecycle mutations (subscribe / charge / pause / resume already do) and expose extend_subscription_ttl / bump_subscription keepers for dormant accounts (already exists).
  • Keeper: Document liveness SLA; consider batch_extend_subscription_ttl keepers for cold subscribers.
  • Error mapping: Preserve isArchivedError handling (codes -32700 / entryExpired / archived) and ErrorRecovery restore flow.

Status

Acknowledged — TTL design is intentional (temporary = safe to recompute, persistent = less likely evicted). Mitigations are docs + UI + keepers; audit should validate extend_ttl coverage and keeper incentives.

Methodology & Non-Goals

What was checked

  • Auth matrix vs lib.rs / admin.rs / migration.rs / upgrade.rs
  • Storage keys (DataKey) and TTL strategy
  • pay_per_use shared-budget + fee split atomicity
  • Frontend allowance/daily-limit flows
  • Pause banner / toast priority, RPC health, allowlists

What was NOT checked

  • Fuzzing / formal verification / full audit
  • Third-party SAC or Freighter internals
  • Off-chain keeper/indexer correctness
  • Economic caps beyond code constants
